2. Enforce strict APP_MODE isolation between demo and live

Refactor code so that:

Demo-only behavior

All demo reset logic, demo seeds, demo fixtures, and sample data operations are never callable when APP_MODE === "live" (or equivalent live flag).

Any demo-related endpoints are guarded with explicit checks:

If in live mode, respond with 403 and a clear log message.

Any shared helpers used by both demo and live must be split or parameterized so that:

Live never calls destructive code intended for demo.

Live-only behavior

Billing, quotas, tier migrations, paid subscription enforcement, and any compliance-related logic should run only when APP_MODE === "live" (or the correct prod flag).

If there is a NODE_ENV / APP_MODE inconsistency (e.g., NODE_ENV=production but APP_MODE=demo), you must:

Fail fast or log loudly when the configuration is inconsistent.

No live resets

Any existing “reset all users”, “reset all data”, “truncate”, or “wipe everything” code must:

Be explicitly marked as demo-only or dev-only.

Not be reachable from live mode via API calls, CLI scripts, or cron.

Create or refactor a single scheduler module for live mode, for example liveScheduler:

“Reset Monthly Quotas”

“Process Monthly Billings”

“Apply Pending Tier Migrations”

Requirements for the scheduler:

Idempotency

Every job must be safe to run multiple times for the same logical period (e.g., month) without double-billing or double-charging.

Use markers in the DB (e.g., job-run records keyed by period) to prevent duplicate side effects.

Safety

Any job that touches money, billing, or Stripe must:

Reconcile against Stripe/subscription state when applicable.

Avoid blindly charging without consistent checks.

If a job previously used demo-like destructive patterns (truncate, etc.), refactor it into update-based, targeted operations.

Observability

Each job run must:

Log start, completion, and duration.

Log errors with stack traces.

Optionally write a job history record (e.g., scheduled_jobs table) with:

job name

started_at

completed_at

status (success/failure)

error message (if any)

Deployment-aware

Ensure the scheduler can be enabled/disabled via env flags so that:

Local dev or Replit can run without accidental double-scheduling.

Production hosting (Fly/Render/etc.) can run a dedicated “worker” or “scheduler” process with CRON_ENABLED=true.
